## 1. Pooled без разброса не публикуется

Все шесть величин подтверждены независимым воспроизведением A
(см. `artifacts/addendum59.json`, раздел `reproduced_a`):

| поле | значение |
|---|---|
| `pooled/fpr_token` | 0,3895509245670678 |
| `folds_over_fpr` (FPR > 0,40) | **4 из 10** |
| `max_fold/fpr_token` | **0,7304347826086957** |
| `std/fpr_token` | 0,1762656426045179 |
| `min_fold/token_f1` | 0,3647388059701492 |
| `max_fold/token_f1` | 0,6730462519936204 |
| `std/token_f1` | 0,1031719059174291 |

**Правило отчётности.** Любая строка с pooled несёт рядом `folds_over_fpr`,
худший фолд и разброс. Pooled 0,3896 держится за счёт хороших фолдов; на
четырёх из десяти норма пробита, на худшем — почти вдвое. Модель нестабильна
между фолдами, и среднее это маскирует.

Это добавляется к протоколу как **жёсткое требование к форме отчёта**, а не как
новая метрика: набор метрик не меняется.

## 2. `pooled/pair_f1 = 0.0` — дефект свода, исправлено

Проверено до прогона B. Ноль **не настоящий**: это чтение несуществующих полей.

В `tools/decode56.py::pooled_metrics` парный F1 собирается из
`support["pair_tp"] / pair_fp / pair_fn`, а `span_exact_f1` — из
`span_counts`. Но `support`, который пишет `tools/rule57.py::_tally`, содержит
другие ключи:

```
flagged_negative_pairs, flagged_negative_tokens, negative_pairs, negative_tokens,
span_fn, span_fp, span_tp, token_fn, token_fp, token_tp
```

Полей `pair_tp`, `pair_fp`, `pair_fn` и `span_counts` там нет — свод читает
нули, отсюда `pair_f1 = 0.0` во всех десяти фолдах.

**Честный парный F1, посчитанный по `outer_predictions` (A, 699 пар):**
`pair_tp = 50`, `pair_fp = 85`, `pair_fn = 189`,
**pair F1 = 0,26738**, precision 0,37037, recall 0,20920.
`fpr_pair = 0,184783`.

Оба исхода из промпта снимаются: ноль не настоящий и не объясняется тем, что
на CV парный F1 структурно нулевой. На test 301 парный F1 был 0,3547; на CV он
**0,2674** — ниже, но того же порядка.

**Следствие для плана.** Свод B считается кодом, который читает предсказания
напрямую (`tools/summarize59.py`), а не агрегатами `decode56.json`-образца.
Пару «A против B» сверяю по всем трём уровням: токены, спаны, пары.

## 3. Какой FPR основной — решено сейчас

| уровень | значение на A |
|---|---|
| `fpr_token` | 0,3896 |
| `fpr_pair` | 0,1891 (в моём воспроизведении 0,1848) |

- **Основной — `fpr_token`.** Консервативный вариант, именно он даёт 0,3896 и
  именно его докладывали все предыдущие разы.
- **`fpr_pair` — вторая строка, всегда.** Запас по нему большой (0,19 против
  0,40), и это законный аргумент в отчёте, но не замена метрики.
- Смена основного уровня после результатов B считается подгонкой и не
  производится.

Порог приёмки 1.7 формулируется как **`fpr_token` ≤ 0,40**, плюс
`folds_over_fpr` рядом.

## 4. Про «потолок 0,644» — как можно и как нельзя

Нельзя: ставить 0,644 и 0,4791 в одну строку как «оракул против переносимого на
одной выборке». Это разные выборки с разными базлайнами.

Можно только так: **0,644 при собственном базлайне 0,5873 на 105 парах
пятифолдового сплита** (превышение над своим базлайном +0,0567, а не +0,132).

Вывод о структурной проблеме декодера от этого не меняется и на 0,644 не
опирается. Он опирается на: Δ = 0,000000 от осей `MAX_SPANS`/`NMS_IOU`/гейта,
один спан на пару, оракул по сетке на самом фолде 0,5095.
