## 1.2 Откуда взялся текущий порог

`summarize59.pick_threshold` выбирает точку сетки с максимальным token F1 **среди точек с `fpr_token ≤ 0,40`**, объединяя счётчики четырёх внутренних фолдов. Ограничение зашито в функцию, а не добавляется после выбора:

```python
if point["fpr_token"] > FPR_LIMIT:   # FPR_LIMIT = 0.40
    continue
```
Поэтому «выбрать 0,45, а потом добавить ограничение» невозможно: 0,45 из выбора исключён по построению. Законный порог по фолдам:

`[0.5, 0.5, 0.49, 0.52, 0.51, 0.5, 0.47, 0.46, 0.47, 0.47]`

Свод на нём: token F1 **0.508888**, fpr_token **0.378691**, exact span **0.234086**, pair F1 **0.303191** — воспроизводит A (`0,508888 / 0,378691 / 0,234086 / 0,303191`).

## Почему не совпало с вашими 0,734 / 0,574 / 0,644

Разбор по числам. У меня на тех же пяти отчётах (351 пара) при 0,45:

| величина | моё значение |
|---|---|
| token recall | **0,644** |
| token precision (все пары, как в A) | 0,452 |
| token precision (только пары с золотом) | 0,687 |
| F1 (все пары) | 0,531 |
| F1 (только пары с золотом) | 0,665 |

**Ваш recall 0,574 ≈ мой recall 0,644, ваш F1 0,644 = мой recall 0,644.** Похоже, что в вашей таблице колонки сдвинуты на одну: 0,644 — это recall, а не F1. Ваша precision 0,734 выше моей 0,687 на подмножестве с золотом; расхождение объясняется тем, какие пары попали в «золотые». Гипотезу о сдвиге колонок я не могу проверить без вашего скрипта — но обе величины, 0,644 и 0,734, воспроизводятся из моих чисел как recall и precision-на-подмножестве.

Проверьте у себя: если 0,644 — это recall, то F1 при 0,45 около 0,53, и «резкого улучшения» нет вовсе.

## 3. Нормировка внутри пары

**Нормировка без абсолютного гейта непригодна: FPR пары 1,000** — при top 20 % субтокенов помечается каждая пара, потому что доля всегда даёт непустое множество. Абсолютное ограничение обязательно; это независимо подтверждает, что гейт нужен, и одновременно показывает, почему низкий гейт опасен: он приближается к «пометить всё».

## Решение

Стадия 2 не запускается: условие п. 1.3 (`fpr_token ≤ 0,40` при гейте 0,45) не выполнено — 0,449. Пункт 1.4 тоже против: спаны втрое длиннее золотых.

**Гейт как рычаг закрывается тем же числом, что и выбор спана: режим 0,45 покупает +0,02 token F1 ценой FPR 0,449 и спанов втрое длиннее золота.** Это не находка, а нарушение нормы, и норма в `pick_threshold` зашита до выбора, а не после.

Линия по порогу и гейту закрыта. Что остаётся открытым и не требует новых прогонов: **B даёт exact span 0,2581 при token F1 0,5165** — это лучшая точка по фрагментам из всех измеренных, и она получена вопросом на входе энкодера. Дальнейший рост возможен только там, а не в декодере.
