# V14 — русские данные, span-классификатор и честная проверка договора

## Итог одной строкой

Договор **не закрыт**, и закрыть его доступными средствами нельзя: русских span-данных с
`doc_overlap = 0` в достижимых источниках нет (RusHallu-RAG — это и есть наш источник, 100 %
документов уже в наших сплитах), а дообучение трансформера заблокировано (GPU нет, весов нет,
HF недоступен, любая энкодер-модель ≥ 48× лимита пакета). Собранная en-проекция RAGTruth
(958 пар, лицензия MIT, `doc_overlap = 0`) при дообучении span-каскада **ухудшает** метрики:
лучший вариант — обучение только на наших данных — даёт val Span `0.3030` (baseline `0.3363`),
mFAVA `0.6483` (baseline `0.6895`); вариант с RAGTruth — Span `0.3000` при mFAVA `0.2548`.
Guard (`Span ≥ 0.50`, `Pair ≥ 0.50`) не пройден ни одним из 8 конфигураций → **reject**,
рантайм не менялся.

## ШАГ 3. Модель

**Трансформер (RuBERT/EuroBERT/ModernBERT) — блокер, честно:**

* GPU нет: `nvidia-smi` отсутствует, `torch.cuda.is_available() = False`, CPU-потоков 1;
* предобученных весов нет: `models/rubert-tiny2` содержит только `config.json` + токенизатор (2,8 MB),
  `pytorch_model.bin` отсутствует, HF Hub недоступен → скачать нечем;
* даже минимальная энкодер-модель не влезет: 29 M параметров ≈ **29 MB int8 / 116 MB fp32** при лимите
  пакета **614 400 B** → 48× / 190× больше; EuroBERT-210m — 342× (int8).

Поэтому обучен **span-классификатор на кандидатах** (HistGradientBoosting на 37 штатных признаках
`spanver.ranker.features`), экспорт деревьев в чистый JSON — рантайм без sklearn/torch.
Признаки, mode-гейт v3 и boundary adjuster **не сбрасывались**.

Тот же эффект был в v11 (listwise/stacker/router) и подтвердился здесь.

### Guard

`Span ≥ 0.50` — максимум 0.3030; `Pair ≥ 0.50` — максимум 0.4110; OOF-прирост отрицательный.
**Ни один пункт договора не закрыт → reject.** Размер модели тоже блокирующий: `local_hgb_v14.json`
= 310 898 B = 3,44× свободного места пакета (90 414 B) — даже при пройденном guard её нельзя было бы
отгрузить без прунинга/квантования.

### Режим с весами: почему не запущен

Договор разрешает держать локально ~500 МБ библиотек и ~530 МБ весов, но в этой песочнице их нет,
а получить их нечем — проверено программно (`tools/speed_v14.py`, секция `weights_mode`):

* `models/rubert-tiny2`: `config.json`, `tokenizer.json`, `vocab.txt`, `special_tokens_map.json` —
  **файла весов нет** (`weight_files = []`);
* `torch.cuda.is_available() = False`, `nvidia-smi` отсутствует → обучение на CPU;
* `huggingface.co` недоступен (разрешены github/codeload/api.github/npm/pypi), поиск по GitHub
  (code search + 3 репозитория с rubert) не дал ни одного `pytorch_model.bin`.

Квантование int8/int4/ONNX применимо только к весам — квантовать нечего. Вместо этого измерена
оптимизация того, что реально исполняется в пакете (деревья):

| представление модели | кандидатов/с | µs/кандидат | размер | Δ к float |
|---|---|---|---|---|
| список словарей (как в `ranker_weights_v3.json`) | 2 208 | 453 | 310 898 B (JSON) | — |
| плоские списки (int-индексы, float-пороги) | 2 177 | 459 | **166 672 B** | 5,6e-17 (бит-в-бит) |
| квантованные пороги (сетка 1/256) | 2 028 | 493 | 310 898 B | ≤ 0.0353 |

Вывод: плоское представление даёт **−46 % размера** без потери точности и без выигрыша в скорости;
квантование порогов ускорения не даёт и меняет предсказания — как оптимизация reject. Скоростной
лимит договора уже выполняется на текущем представлении.

## Почему блокер и что дальше

1. **Данные**: единственный достижимый русский span-корпус с разметкой — RusHallu-RAG, и он уже
   израсходован (100 % doc_overlap). Нужен либо доступ к HF (ru-часть hallucination-detection-benchmark,
   RU-RAGTruth, полный mFAVA), либо новый русский корпус документов (rusBEIR LFS недоступен) —
   например SberQuAD/ruSciBench исходники с последующей programmatic-генерацией по v11-рецепту.
2. **Стиль**: даже с новыми данными нельзя смешивать стили «короткая клауза» и «длинный clause/whole»
   без выравнивания по длине спана — это прямо показал провал mFAVA (0.69 → 0.25) на mixed-обучении.
3. **Ёмкость рантайма**: 37 признаков + GBDT в пакете ≤ 0.6 MB — потолок; v9-аудит показывает, что
   oracle по нашим кандидатам даёт Span 0.91, значит данные/ёмкость, а не генерация кандидатов —
   узкое место. Трансформер в пакет не влезает (≥ 48× лимита), дистилляция требует весов.
