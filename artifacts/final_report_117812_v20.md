# V20 — ранжировщик на синтетике v19: обучен, измерен, переноса нет (reject по Span)

## Итог одной строкой

Датасет v19 (1659 пар / 1354 спана, реальный клаузовый стиль, `doc_overlap = 0`) скачан, сверен по
SHA-256, зафиксирован в git до обучения (шаг 0 → commit `a090ee0`). На нём обучены 5 вариантов
ранжировщика + 3 линейных переобучения + смеси с риском v11. Данные **выучиваются in-domain

cross-domain AUC 0.62–0.71 против 0.7425; лучший val Span 0.3670 (+0.005 к baseline 0.3621 — шум);
OOF Span 0.2295 против требуемых 0.2637. **Guard не пройден: reject по Span.**

## Что это доказывает и что делать дальше

1. **Гипотеза «синтетика в реальном стиле закроет Span» опровергнута измерением.** v19 — не флипы:
   в нём clause 52 % / whole 37 % / short 11 %, doc_overlap 0, oracle 0.9548; in-domain AUC 0.984.
   И всё равно перенос на реальные пары — 0.62–0.71 AUC, Span ≤ 0.367.
2. **Блокер не в данных, а в признаках.** 37 лексических признаков (tf-idf-косинус с документом,
   границы, длины, типы) упираются в AUC ≈ 0.74 — это и есть потолок ручного v11. Чтобы Span ≥ 0.50,
   нужен AUC ≳ 0.88–0.90 кросс-доменно, а такой сигнал даёт только модель, читающая документ и ответ
   совместно.
3. **Что сработает (по приоритету):**
   * **GPU + cross-encoder** (`rubert-tiny2`/`rubert-base`, пара «документ ⊕ кандидат» → вероятность):
     v19 даёт втрое больше span-супервизии, чем реальные 549 пар, и именно в нужном стиле; обучение
     на real+v19 с последующей калибровкой на val — единственный реалистичный путь к Span ≥ 0.50.
     На 2 CPU-ядрах это ~50 мин/эпоху и 0.6 с/пара на инференсе (в 200× выше лимита §4.1), нужен GPU
     для обучения + квантование/каскад для рантайма.
   * **Признаки из внимания LM** (v17: 14 span-level признаков, AUC по одному 0.50–0.60) — пересобрать
     на v19 и добавить к 37: слабый, но единственный доступный на CPU путь.
   * **Продуктовое решение**: принять Span ≥ 0.37 при Token 0.65 / Pair 0.52 / FPR 0.11 — рантайм уже
     отдаёт корректные фрагменты в 37 % случаев.
4. Дальше по договору без GPU/новых реальных данных циклы будут повторять один и тот же потолок —
   это зафиксировано в v18 и подтверждено измерением v20.
